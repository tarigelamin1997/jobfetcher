# ADR-0036 — Gold-filter rejection lineage (bounding the read without freezing the decision)

**Status:** Accepted · **built 2026-09-01**, branch `feat/gold-rejection-lineage` · **CRUCIAL tier** (schema migration `0007` — both human checkpoints required; the live deploy is a separate checkpoint) · resolves [ERR-010](../ledgers/errors.md)

## Context

The daily pipeline returned `statusCode: 500` on **every run from 2026-07-25 to 2026-09-01 — 38 consecutive days** — and the last digest SES sent was 2026-07-24. The cause was `get_silver_postings()`: `select(tables.posting)`, all 22 columns, unbounded, for every `status='silver'` row, over the RDS Data API's hard **1 MB** result cap. Measured live at discovery: **1,022 rows / 3,110 kB**, of which **1,143 kB was `description`** — written once, read nowhere. The columns the mapper actually consumes total **109 kB**.

Two things made this inevitable rather than unlucky.

**The read grew with history, by design.** `apply_gold_filter` left every non-fit at `status='silver'`, so each run re-read and re-filtered *every posting ever rejected*. The daily read was O(all history) on a monotonically growing table.

**The limit was considered and mis-sized.** [ADR-0014](0014-operational-store-aurora-serverless-data-api.md) chose the Data API to keep the Lambda out of a VPC (a ~$32/mo NAT gateway is the alternative, for a tool whose whole cost model is scale-to-zero) and dismissed the cap in writing: *"the Data API has request/result-size limits (irrelevant at 10–30 rows/day)."* 10–30 rows/day is the **ingest rate**; the read is **cumulative**. The ADR sized a stock by its flow. The transport choice was and remains correct — the capacity assumption was not.

There is a third finding worth stating because it shapes what this ADR does *not* do: INV-002's `PipelineReturned500` alarm fired on all 38 days and delivered two emails a day to the operator. **Detection was never the gap.** No new alarm is added here.

## Decision

Three changes. One migration (`0007_gold_filter_hash`, additive, no backfill), no infra change, no new dependency.

**1 — Column projection (fixes payload width).** `_SILVER_COLUMNS` and `_GOLD_COLUMNS` are declared in `adapters/repository_postgres.py` immediately beside `_dissected_from_row`, so a projection and the mapper that consumes it cannot drift apart. Applied to `get_silver_postings` and `get_gold_candidates`; single-row reads (`get_posting`) keep `select(tables.posting)` because one row cannot reach the cap. **3,110 kB → 109 kB**, roughly 28× headroom.

**2 — Rejection lineage (fixes the growth).** A non-fit is terminal-stated `status='rejected'` **and stamped** with `gold_filter_hash` — the decision context that rejected it. `get_silver_postings(filter_hash=…)` returns rows never judged (`status='silver'`) plus rejections whose stamp `IS DISTINCT FROM` the current hash. The daily read becomes O(new postings) on an unchanged config, and a config change re-opens the entire rejected backlog.

`IS DISTINCT FROM`, not `!=`, is load-bearing: a NULL stamp (a pre-0007 row, or one written by an older build) must count as *unjudged*. Under `!=` the comparison is NULL, the row never matches, and it vanishes from every future read — the exact permanent-loss failure this design exists to prevent.

**The hash is `compute_filter_hash`, deliberately NOT `compute_profile_hash`.** The existing hash (`handlers/pipeline.py`, migration 0004) covers what *scoring* judges against: the profile plus `threshold` / `hard_floor` / `near_miss_band`. It does **not** include `spec.targeting`. The gold filter reads `targeting.job_titles`, `.countries` and `.cities` (`filter_deterministic.py`) as well as `profile.preferences.avoid_keywords`. Stamping rejections with the scoring hash would leave a `job_titles` edit — the single most likely config change anyone makes — with an unchanged stamp, so every posting rejected under the old titles would stay closed forever, silently. `compute_filter_hash` hashes the whole profile, the whole spec, and the strategy name: it **over**-invalidates (editing `threshold` re-opens the backlog for a filter pass that could not change) and never **under**-invalidates. The asymmetry decides it — over-invalidation costs one cheap deterministic pass over 109 kB; under-invalidation loses a real job with nothing to notice.

**3 — A legible billing failure.** `LlmBillingError` (HTTP 402) is its own type, checked before the model-not-found body heuristic that could otherwise swallow it, never retried, counted as `billing_blocked` in the ingest summary, and logged **once** with the operator action. During the outage the DeepSeek account also ran dry, and the run summary read `{fetched: 137, silvered: 0, skipped: 137}` — indistinguishable from ordinary attrition, under 137 identical per-item warnings.

## Alternatives Considered

- **A plain terminal `status='rejected'`, no stamp.** The cheapest read, and the obvious fix. Rejected because it silently discards a real property the broken behaviour provided *by accident*: because rejected postings stayed `silver`, editing your config re-evaluated every posting ever rejected. `reassess` cannot substitute — it replays `status='scored'` rows (`get_scored_for_reassess` filters on that), so a posting killed at the gold filter never reaches it. This alternative would have frozen gold decisions permanently, with nothing announcing the loss. The stamp costs one nullable column.
- **An age cutoff (`gold_filter_max_age_days`), mirroring `reassess_max_age_days`.** Rejected: it is a heuristic where an exact answer exists. It would bound the read, but it discards postings by *when they arrived* rather than *whether the current config has judged them* — so a widened `job_titles` would still fail to rescue anything older than the window. It also required a new required `SearchSpec` field, which is a coupled config-and-code deploy (see Consequences).
- **Keyset pagination over the silver read.** Rejected as subsumed: it fixes payload *height* generically, but leaves the O(all-history) scan intact — the same total bytes in more round-trips, forever. Worth revisiting only if a single page ever needs bounding on its own.
- **An append-only `gold_event` table, mirroring `score_event` ([ADR-0025](0025-score-event-lineage.md)).** More consistent with the project's lineage pattern, and genuinely tempting. Rejected on P1: deciding whether to re-open a rejection needs only the *current* decision context, not the full history of every gold verdict. One nullable column answers the question; a table answers a question nobody has asked yet. It remains an additive follow-on if gold-decision history ever earns its keep.
- **ClickHouse (or any column store) for the read path.** Raised and rejected. It does not address the fault — this was read amplification (asking for 30× more data than the code consumes) over a capped transport, and swapping the store does not stop the query asking for too much. At **1,022 silver rows and 401 scored rows** the entire database is a few megabytes; Postgres serves this for years. Decisively, it breaks the cost model the whole architecture rests on: Aurora `min_capacity = 0` gives ~$0 idle for 23 hours a day, and ClickHouse has no equivalent at the bottom end. Per [ADR-0002](0002-tool-minimalism-wins.md), a portfolio rationale is not a justification — and introducing a column store as the fix for a `SELECT *` bug would be exactly the rationalized version that ADR warns about.
- **Lambda in a VPC with psycopg2** (no result cap, real cursors). Rejected — this re-litigates ADR-0014 and its reasons still hold: NAT gateway cost, ENI cold-start penalty, connection-pool management, all for a daily batch of 10–30 postings.

## Consequences

- **Easier:** the daily read is bounded by *new work*, not by history. On an unchanged config the gold filter reads only postings it has never judged; the 1 MB cap moves from "a growing certainty" to "unreachable at this scale."
- **The re-open property is now explicit rather than accidental**, and testable: `tests/test_gold_filter.py` pins that a changed context re-opens the backlog, that an unchanged one does not re-read it, and that a **fail-open** posting (a `FilterError` — a verdict we never actually got) is never stamped rejected, so a transient filter outage cannot permanently close postings.
- **Honest limitation — the hash caches a sample, not a verdict, under `LlmFilterStrategy`.** The LLM is non-deterministic, so "same hash" does not guarantee "same decision" the way it does for `DeterministicFilterStrategy`. Acceptable because deterministic is the default and the LLM strategy has never been selected in production, and `strategy_name` is in the hash so a swap re-opens everything. Stated here rather than left to be discovered.
- **No backfill, self-healing.** Every existing row has a NULL stamp and is therefore unjudged: the first run after deploy reads the 1,022-row backlog once (109 kB, projected), filters it, and stamps each row. One expensive run, then cheap.
- **Migration ordering.** `ALEMBIC_HEAD` must be bumped in **both** `terraform/lambda.tf` and `_EXPECTED_MIGRATION_HEAD` in `handlers/pipeline.py` — the staleness unit test covers only the second, and the first *overrides* it at runtime, so a stale `lambda.tf` would let the smoke gate pass against the wrong schema. Recorded as a standing gap in the [backlog](../ledgers/backlog.md).
- **A deploy hazard avoided, and written down anyway.** Because no new `SearchSpec` field is required, this ships without the coupled config-and-code rollout that the age-cutoff alternative would have forced. That hazard is real for the *next* knob — `SearchSpec` is `extra="forbid"` with every field required, so a new required field breaks in both directions during rollout — and is now noted in the [deploy runbook](../runbooks/deploy.md).
- **Residual weakness, deliberately not closed here:** an alarm that fires every day for 38 days is noise, and this project has no mechanism that escalates a *persistent* alarm differently from a one-off. Adding another alarm would be treating the wrong failure. Logged in the [backlog](../ledgers/backlog.md) as a real open item.
- **Four more unbounded reads share the same ceiling** and are recorded, not fixed: `get_scored_for_reassess`, `get_scored_shortlist`, and `get_all_scored` (401 rows / 274 kB of LLM prose today — the next to approach the wall). `get_gold_candidates` is fixed here by projection.
- **Not yet live.** Built and tested (468 unit tests green, 6 new integration tests, `ruff` clean, migration validated offline); the deploy and live validation are a separate human checkpoint.
