# Ledger · Error & Incident Log

> Every error, incident, deviation, or chaos-discovered gap is logged here — **constructed live, not reconstructed later.** Read this log *before* re-attempting any fix (a solution that reintroduces a known-failed approach is a documentation failure, not an engineering one). Paste error messages **verbatim** — the exact tokens are the searchable value. A stage cannot close with an open error.

### ERR-002 — Docker Hub anonymous pulls return 403 (local Postgres for storage tests)   [Resolved]
- Stage: dev-infra (the dedicated `jobfetcher-db` local Postgres for C-2 storage tests) · Layer: tooling/connectivity · Type: connectivity / dependency
- Discovered: 2026-06-26 · Resolved: 2026-06-26 · Source: implementation (setting up local-Postgres tests)

1. **What happened?** Every `docker pull` from **Docker Hub** returned `403 Forbidden` on the CloudFront blob CDN — even `hello-world` — while pulls from **MCR / GHCR / mirror.gcr.io** succeeded. So the `jobfetcher-db` docker-compose couldn't fetch `postgres:16-alpine`.
2. **Why?** Docker Hub **anonymous-pull blocking** from this network/CDN — the registry refused unauthenticated blob fetches. **NOT** auth (no login configured/needed), **NOT** a corporate proxy, **NOT** disk/space. The "even hello-world fails, but other registries work" signature is the tell.
3. **How?** C-2's storage tests run against a real local Postgres (not LocalStack — [ADR-0018](../adr/0018-persistence-sqlalchemy-data-api-repository.md)); standing up `jobfetcher-db` required the Postgres image from Docker Hub, which hit the 403 wall.
4. **How fixed?** Added a **registry mirror** — `"registry-mirrors": ["https://mirror.gcr.io"]` in Docker Desktop → Settings → Docker Engine; a fresh `postgres:*-alpine` pull then succeeded. The compose image is also overridable via `${JOBFETCHER_DB_IMAGE:-postgres:16-alpine}`.
5. **Prevention + Detection:** the registry mirror persists in Docker config; `docker-compose.yml` pins the image + allows the env override so a blocked registry is a one-line swap. **Detection:** a `docker pull` failing `403` on the blob CDN *while MCR/GHCR/mirror.gcr.io work* = anonymous-pull blocking → use the mirror (don't chase auth/proxy).
- **Blast radius:** local storage tests (C-2 onward) only; **no production impact** (the deployed store is Aurora, not a container).
- **Prevention implemented?** Yes — registry mirror + the `${JOBFETCHER_DB_IMAGE}` override (commit `90ff53d`).

### ERR-003 — GitGuardian flagged a local-dev example password   [Resolved — false positive, hardened anyway]
- Stage: dev-infra / PR hygiene (C-2 storage PR) · Layer: tooling · Type: config (secret-scan false positive)
- Discovered: 2026-06-26 · Resolved: 2026-06-26 · Source: GitGuardian on the PR

1. **What happened?** GitGuardian raised a **Generic Password** alert on a literal local-dev password (`postgres`/`jobfetcher`) committed in `docker-compose.yml` + an integration-test docstring. (The alert id `#18608761` actually traced to a *separate* `tradesense` repo, but the jobfetcher literal tripped the same heuristic.)
2. **Why?** A **hardcoded credential literal** in a committed file matches the generic-password detector — even when it's a throwaway local-dev value, not a real secret. The scanner can't tell "example" from "real."
3. **How?** The `jobfetcher-db` compose + a test docstring carried a bare local-dev password literal.
4. **How fixed?** **Env-interpolated** the value — `${POSTGRES_PASSWORD:-jobfetcher}` in `docker-compose.yml` + the test docstring; the squash-merge kept the bare literal out of `main`.
5. **Prevention + Detection:** example/local credentials are **env-interpolated with a default**, never bare literals; the per-PR secret scan (GitGuardian + the build's own `git diff` scan) is the **detection**. No real credential was ever exposed.
- **Blast radius:** none — a false positive on a non-secret local-dev value.
- **Prevention implemented?** Yes — the env-interpolation pattern (compose + test docstring).

### ERR-004 — Alembic over the Data API crashes on `%`-encoded ARNs (configparser interpolation)   [Resolved]
- Stage: Step 10 deploy (schema creation on live Aurora via `alembic upgrade head` over the Data API) · Layer: persistence / migrations · Type: config (string interpolation)
- Discovered: 2026-06-29 · Resolved: 2026-06-29 · Source: implementation (live v0.1.0 deploy)

1. **What happened?** Running `alembic upgrade head` against live Aurora over the **RDS Data API** crashed inside `migrations/env.py` when it set the connection URL. The aurora-data-api URL embeds the cluster + secret **ARNs**, which are `%`-encoded (`arn:aws:rds:…` → `…%3A…`); Alembic's `config.set_main_option(...)` routes the value through Python's `configparser`, whose **`%`-interpolation** tried to expand `%3A` / `%2F` as interpolation tokens and raised on the malformed reference.
2. **Why?** `configparser` treats `%` as the interpolation sigil; a literal `%` in a value must be **doubled (`%%`)** to survive. The Data-API URL is the first migration URL to *contain* `%`-encoded ARNs, so the bug had never been reachable before.
3. **How?** Local migrations + tests run **psycopg2** against a container Postgres, whose URL is `postgresql://user:pass@host/db` — **no ARNs, no `%`** — so `configparser` never had anything to interpolate. CI's postgres service has the same psycopg2 URL. The Data-API path that carries the `%`-encoded ARNs is **only exercised on a real deploy**, so the crash first appeared at `alembic upgrade head` on live Aurora.
4. **How fixed?** In `migrations/env.py`, **escape `%`→`%%`** in the resolved Data-API URL before handing it to `config.set_main_option(...)`, so configparser stores the literal ARN characters. Migration then ran clean and created the v0 schema on live Aurora.
5. **Prevention + Detection:** the escape is in `env.py` so any future migration over the Data API is safe. **Detection — the real gap:** *no test exercises the Aurora Data-API path* (local = psycopg2, CI = postgres service), so neither the unit pyramid nor CI could ever surface a Data-API-URL-specific bug — **only the live deploy did.** The honest detection lesson is that a **live smoke run against real Aurora** is the gate that catches Data-API-specific bugs; a future **minimal live-Data-API test** (run only with credentials, skipped in CI) would catch this class earlier.
- **Blast radius:** schema creation on deploy — *blocks every deploy* (no schema ⇒ no pipeline) until fixed; no data impact (caught before any run).
- **Prevention implemented?** Yes — the `%`→`%%` escape in `migrations/env.py` (v0.1.0 deploy fix). Detection gap (a live-Data-API test) noted, not yet built.

### ERR-005 — aurora-data-api dialect rejects `cluster_arn` connect-kwarg (wrong param name)   [Resolved]
- Stage: Step 10 deploy (Lambda `resolve_db_url` building the SQLAlchemy URL) · Layer: persistence / connectivity · Type: config (wrong kwarg name)
- Discovered: 2026-06-29 · Resolved: 2026-06-29 · Source: implementation (live v0.1.0 deploy)

1. **What happened?** The pipeline's first DB call on live Aurora raised **`connect() got an unexpected keyword argument 'cluster_arn'`**. `handlers/pipeline.py` `resolve_db_url` built the SQLAlchemy URL with a `cluster_arn=` query parameter; the **`sqlalchemy-aurora-data-api`** dialect maps URL query params **straight through to its `connect()` kwargs**, where the parameter is named **`aurora_cluster_arn`** — so `cluster_arn` arrived as an unknown kwarg and `connect()` rejected it.
2. **Why?** The dialect's documented connect kwarg is `aurora_cluster_arn` (and `secret_arn`), not the shorter `cluster_arn` the code assumed. The query-param→kwarg pass-through means the name must match the dialect's `connect()` signature **exactly**.
3. **How?** Same structural blind spot as ERR-004: the aurora-data-api dialect's `connect()` is **only invoked on the real Data-API path**. Local psycopg2 and CI's postgres service use a *different dialect entirely*, so they never call `aurora_data_api.connect()` and never validate its kwarg names. The wrong name was reachable only on a live deploy — and it would have broken **every** deploy, not an edge case.
4. **How fixed?** Renamed the query param in `resolve_db_url` to **`aurora_cluster_arn`** (matching the dialect's `connect()` kwarg). The pipeline then connected to live Aurora over the Data API and ran end-to-end (`statusCode 200`, fetched 10 → … → email sent).
5. **Prevention + Detection:** the corrected kwarg name is in `resolve_db_url`. **Detection — the same real gap as ERR-004:** *no test exercises the Aurora Data-API path*, so the dialect's actual `connect()` signature is never validated by local tests or CI; only the **live smoke run against real Aurora** caught it. The detection lesson stands: a **live deploy is the gate** for Data-API-dialect bugs, and a future **minimal live-Data-API test** would pin the kwarg contract earlier.
- **Blast radius:** the Lambda's DB connection — *blocks every deploy / every run* (no connection ⇒ no pipeline) until fixed; no data impact (caught on the first live invocation).
- **Prevention implemented?** Yes — the `aurora_cluster_arn` rename in `handlers/pipeline.py` (v0.1.0 deploy fix). Detection gap (a live-Data-API test) noted, not yet built.

### ERR-006 — one DeepSeek 503 killed the whole run (no retry + asymmetric failure isolation)   [Resolved]
- Stage: M1 P2 live run (silver dissection + scoring) · Layer: LLM transport / orchestration · Type: missing resilience (no retry) + inconsistent error handling
- Discovered: 2026-07-02 · Resolved: 2026-07-02 (M1/H-1, PR #14) · Source: live full-sweep run (`complete01`)

1. **What happened?** A completing invoke returned **`statusCode 500`** with `LlmError: HTTP 503: {"error":{"message":"Service is too busy. We advise users to temporarily switch to alternative LLM API service providers."}}`. One transient DeepSeek overload aborted an entire pipeline run — gold/score/notify never ran.
2. **Why?** Two gaps compounded. (a) `OpenAICompatLlmClient.complete()` made **exactly one** HTTP attempt — any non-401/404 status (incl. 503) raised `LlmError` immediately, no retry/backoff. (b) **Asymmetric isolation:** `score_gold` caught `(ScorerError, LlmError)` per item, but `land_silver` caught only `DissectionError` — so an `LlmError` raised inside `Dissector.dissect` propagated raw and crashed the run.
3. **How?** Provider overload (`503`) is transient and common at scale, but the client treated it as fatal, and the dissection path had no isolation net for it. Local/CI tests mock the LLM and never exercise a real provider 503, so the gap was invisible until a live run hit an actual DeepSeek overload.
4. **How fixed?** H-1 (PR #14): `complete()` retries **only transient** failures (HTTP 429/500/502/503/504 + connection/timeout) with **exponential backoff + full jitter** (`LlmConfig.max_retries=3`, `backoff_base_s=1.0`); 401/404/other-4xx still fail fast. `land_silver` now catches `(DissectionError, LlmError)` → skip one posting, never the run (symmetric with `score_gold`). Re-validated live (revalidate01): **15 dissect failures + 0 score failures isolated**, `statusCode 200`, digest sent.
5. **Prevention + Detection:** retry policy lives in `adapters/llm_openai.py` (config-tunable); isolation is symmetric across both LLM stages. **Detection:** unit tests assert retry-to-success, exhausted-retries, never-retry-401, fail-fast-4xx, and the `land_silver` LlmError-skip; the live re-validation is the behavioral gate. **Lesson:** a mocked-LLM test suite can't catch provider-resilience gaps — a live run under real load is the gate, and every external call needs an explicit transient-vs-fatal policy.
- **Blast radius:** a whole run per transient blip (no partial progress past the failing stage) until fixed. No data corruption (bronze immutable; upserts idempotent).
- **Prevention implemented?** Yes — retry+jitter + symmetric isolation (v0.2.0 / [ADR-0021](../adr/0021-m1-pipeline-hardening.md)).

### ERR-007 — AWS async auto-retry re-fetched a timed-out run (quota + token burn)   [Resolved]
- Stage: M1 P2 live run (async invoke of the full sweep) · Layer: infra / Lambda invocation config · Type: platform default mismatched to a long idempotent-but-expensive job
- Discovered: 2026-07-02 · Resolved: 2026-07-02 (M1/H-2, PR #15/#17) · Source: live poll (bronze crept 155→161 after a timeout)

1. **What happened?** After the serial full-sweep run timed out (15-min cap), the DB showed bronze climbing again minutes later — **a second invocation had started on its own**, re-fetching the whole sweep from scratch.
2. **Why?** The function was invoked **asynchronously** (`--invocation-type Event`), and **AWS retries a failed async invocation up to 2× by default**. A 15-min run that times out looks like a failure, so AWS re-queued it — each retry re-ran fetch (JSearch quota) + re-dissected (tokens) on a run that would only time out again.
3. **How?** The default async retry policy is sensible for short idempotent handlers, but wrong for a long-running batch that resumes on its *own* schedule (EventBridge tomorrow / a manual re-invoke). No `event_invoke_config` was set, so the default (2 retries) applied.
4. **How fixed?** Mitigated live via CLI (`put-function-event-invoke-config --maximum-retry-attempts 0`), then codified in Terraform: **`aws_lambda_function_event_invoke_config { maximum_retry_attempts = 0 }`** (H-2). Combined with H-2's deadline guard (runs now return `partial` cleanly instead of timing out), the failure that triggered the retry is itself gone. Verified post-deploy: `get-function-event-invoke-config` → `MaximumRetryAttempts: 0`.
5. **Prevention + Detection:** the retry-0 config is in `terraform/lambda.tf` (IaC, no drift). **Detection:** a live invoke no longer spawns a re-fetch; the deadline guard makes timeouts impossible. **Lesson:** platform defaults (async retry) must be matched to the job's shape — a long, self-resuming, expensive job must opt out of blind platform retries.
- **Blast radius:** wasted JSearch quota (a scarce free-tier resource) + LLM tokens per retry; no data corruption (idempotent upserts + `already`-skip + the `run_log` send-once guard meant even overlapping runs produced one email).
- **Prevention implemented?** Yes — `maximum_retry_attempts=0` in Terraform + the deadline guard (v0.2.0 / [ADR-0021](../adr/0021-m1-pipeline-hardening.md)).

### ERR-008 — AWS CLI client-side retry re-invoked a long synchronous reassess (~3× token spend)   [Resolved]
- Stage: v0.7.0 release live smoke (reassess invoke) · Layer: client tooling / invocation pattern · Type: client default mismatched to a long synchronous call (ERR-007's client-side twin)
- Discovered: 2026-07-08 · Resolved: 2026-07-08 (procedure) · Source: CloudWatch (extra full runs) + `score_event` counts (771 ≈ 3 × 228 — the lineage log itself exposed the duplicates)

1. **What happened?** A synchronous (`RequestResponse`) `aws lambda invoke` of `{"mode":"reassess"}` timed out **client-side**; the CLI's default retry re-sent the request, spawning additional full runs — the DB showed ~3 passes' worth of `score_event` rows (771 for ~228 postings) where one was intended.
2. **Why?** botocore's standard retry mode treats a slow response as retryable, and an 11–12-minute Lambda response exceeds the client read timeout. **`maximum_retry_attempts=0` (ERR-007's fix) governs *async* invokes only** — it cannot stop the *client* from retrying a synchronous call.
3. **How?** Long LLM batch + synchronous invocation + default client retry policy. Idempotency held throughout (append-only events, idempotent upserts, send-once guard) — the cost was duplicate LLM spend and `previous_score` churn, not corruption.
4. **How fixed?** Procedure: long-running invokes go **async** (`--invocation-type Event`, protected by the server-side retry-0) or, if synchronous, with the client retry disabled (`AWS_MAX_ATTEMPTS=1`) + an adequate `--cli-read-timeout`. Registered in the [procedure registry](procedure-registry.md).
5. **Prevention + Detection:** procedure-registry entry (invocation pattern per job shape). **Detection:** `score_event` counts per `run_id` — Run 1's lineage log is what made the duplicates visible at all. **Lesson:** retry policies exist on **both** sides of an invocation; each must be matched to the job's shape (the server side was fixed in ERR-007; the client side is this entry).
- **Blast radius:** ~2 extra reassess passes of pro-model tokens (DeepSeek ≈ pennies) + benign `previous_score` churn; zero corruption.
- **Prevention implemented?** Yes — procedure (the *invocation pattern per job shape* [registry row](procedure-registry.md)). **Run-5 decision (2026-07-08, [ADR-0029](../adr/0029-ops-hardening.md)): procedure-only** — the pattern is encoded in the [deploy runbook](../runbooks/deploy.md) §2 one-liner (`AWS_MAX_ATTEMPTS=1` + `--cli-read-timeout`); the once-mooted `scripts/invoke.py` wrapper was **explicitly decided against**, deferred until real ops friction demands it.

### ERR-009 — Aurora scale-to-zero resume killed runs at the first DB touch (no resume wait)   [Resolved]
- Stage: daily operation (cron + manual invokes on the v0.7.0 stack) · Layer: persistence / Aurora Serverless v2 · Type: dependency (platform resume window) + missing resilience
- Discovered: 2026-07-08 (first kill; pattern confirmed 2026-07-09) · Resolved: 2026-07-09 (branch `fix/aurora-resume-retry`) · Source: live kills (CloudWatch logs + missing digests)

1. **What happened?** Three identical dead runs, each dead **3–5 seconds** after start: a 2026-07-08 ~05:59Z sync invoke (manual invoke; RequestId not captured), the 2026-07-09 **06:00:38 daily cron** (RequestId `62d5544a`), and the 2026-07-09 19:23:59 async reassess (RequestId `0138800d`). Each died at the run's FIRST DB touch (`upsert_profile`) with `botocore.errorfactory.DatabaseResumingException` — verbatim: *"…is resuming after being auto-paused. Please wait a few seconds and try again."* — surfacing through SQLAlchemy as a `StatementError`, caught by the handler's outer catch → `statusCode 500` → no retry (`maximum_retry_attempts=0`, ERR-007) → dead run, **no digest**.
2. **Why?** Aurora Serverless v2 scales to zero when idle (the deliberate ~$0-idle cost model); the first query against a paused cluster fails with the resume signal while the cluster wakes (**~15–30s**). The pipeline had **no resume wait** — it treated "briefly asleep" as fatal — and the retry-0 decision (correct for its own reasons, ERR-007) guarantees nothing re-runs a returned 500. ERR-009 is the one failure class that genuinely needed a (targeted, in-process) retry.
3. **How?** **Latent since v0.1, masked by dev activity:** every prior live run happened while iteration kept Aurora warm at invoke time (or other queries had just woken it). The first cron fire on a morning with no preceding dev activity caught the cluster asleep — the tool's *actual* at-rest daily shape, unreachable during active development. The masking lifted exactly when development paused.
4. **How fixed?** `wait_for_db_resume(engine, budget_s=90.0, interval_s=5.0)` in `src/jobfetcher/db/engine.py`: probes a trivial `SELECT 1`; if the exception's **root cause** is the resume signal, sleeps and retries within the budget (each wait logged at INFO — cold starts are now visible in CloudWatch); **any other exception re-raises immediately** (never masks a real failure); budget exhaustion re-raises the resume error loudly. Matching is **name-based** — `type(e).__name__ == "DatabaseResumingException"` walking the `.orig`/`__cause__` chain (botocore *generates* the class from the service model, so it can't be imported), + the *"resuming after being auto-paused"* message substring as belt. Called at **both** repo-construction sites in `handlers/pipeline.py` — the smoke gate's own repo (Run 5 / ADR-0029 constructs it before the shared point) and the shared pipeline repo before the profile sync — **two explicit call sites, every mode's first query protected**; the 90s budget costs nothing against the 900s Lambda timeout + deadline margin. Local Postgres is unaffected (the exception doesn't exist there; the first probe succeeds in ~ms).
5. **Prevention + Detection:** unit tests pin the whole contract — retry-to-success (attempt-counted), immediate re-raise on non-resume (zero sleeps), budget exhaustion at ~budget/interval attempts, the `StatementError` `.orig`/`__cause__` chain walk, the message-substring belt, and the handler call order in every mode (`tests/test_db_resume.py`, `time.sleep` patched throughout). **Detection — the ironic gap:** Run 5's new alarms **cannot see this failure**: the handler *catches* the exception and *returns* a 500, so the invocation itself SUCCEEDS — invisible to both the Errors alarm and the dead-man switch (the function ran). That returned-500-vs-raised blind spot is exactly the gap [ADR-0029](../adr/0029-ops-hardening.md) documents (Run 5's ops hardening); ERR-009 is its first live instance — until a returned-500 detector exists, the only observable symptom is the *absent digest email*. **A second detection gap, found while validating this very fix:** ALL `jobfetcher` INFO telemetry — including this fix's own wait logs — was invisible in production (Lambda's Python runtime leaves the root logger at WARNING and no package level was ever set), so the ground truth for the kills was the DB lineage log (771 events written, zero matching INFO lines in the log group), not CloudWatch — fixed in this same run: the handler now sets the `jobfetcher` package logger from `$LOG_LEVEL`, default INFO (safe-fallback to INFO + a WARNING on a junk value). **Lesson:** scale-to-zero is a feature of the cost model, so the application must own the resume wait; and error-shape decisions (catch-and-return vs raise) silently decide what monitoring can ever see.
- **Blast radius:** 3 dead runs (2 daily digests never sent, 1 reassess no-op); **zero data corruption** (each run died before its first write). Unfixed, every cold-morning cron would die the same way — the daily tool was effectively broken *at rest*.
- **Prevention implemented?** Yes — `wait_for_db_resume` + handler wiring + unit tests (branch `fix/aurora-resume-retry`).

### ERR-010 — The gold-filter read outgrew the Data API's 1 MB result cap; 38 consecutive daily runs died unnoticed   [Resolved]
- Stage: daily operation (the unattended cron on the v0.12.0 stack) · Layer: persistence / RDS Data API · Type: logic (unbounded read) + a capacity assumption that was measured against the wrong quantity
- Discovered: 2026-08-31 (during a codebase review, by inspecting the deployed stack — **not** by anyone reading the alarm) · Resolved: 2026-09-01 (branch `feat/gold-rejection-lineage`) · Source: live kills (CloudWatch metrics + logs)

1. **What happened?** Every daily run from **2026-07-25 to 2026-08-31 inclusive — 38 consecutive days —** returned `statusCode: 500`. The last digest email SES sent was **2026-07-24**. The cron never missed a beat (46/46 invocations in the window); it woke, crashed, and went back to sleep. Verbatim, from the 2026-08-31 06:00 UTC run:
   > `botocore.errorfactory.UnsupportedResultException: An error occurred (UnsupportedResultException) when calling the ExecuteStatement operation: The result exceeds the size limit 1 MB.`

   The traceback pinned it exactly: `handlers/pipeline.py:421 → core/ingest.py:368 apply_gold_filter → repository_postgres.py:242 get_silver_postings`.
   A **second, independent** failure was layered on top by then: the DeepSeek account had run out of credit, so every dissection returned `HTTP 402: {"error":{"message":"Insufficient Balance",...}}` and the run summary read `{'fetched': 137, 'bronzed': 137, 'silvered': 0, 'skipped': 137}`. Either fault alone was enough to break the tool.
2. **Why?** `get_silver_postings` ran `select(tables.posting)` — **all 22 columns** — for every `status='silver'` row, unbounded, and `.all()`'d it. The RDS Data API is an HTTPS request/response API with a hard 1 MB cap on the serialized result; it has no cursor and no streaming. Measured on the live table at discovery: **1,022 silver rows / 3,110 kB**, of which **1,143 kB was `description`** — the full JD text, written at `repository_postgres.py:137` and **read nowhere** (`_dissected_from_row` never touches it). The twelve columns the mapper actually consumes total **109 kB**.
   The growth engine was a separate design choice: `apply_gold_filter` left every non-fit at `status='silver'`, so each run re-read and re-filtered **every posting ever rejected**. The daily read was O(all history) and could only ever grow.
   **The root assumption, and it is the real lesson.** [ADR-0014](../adr/0014-operational-store-aurora-serverless-data-api.md) considered this exact limit and dismissed it, in writing: *"the Data API has request/result-size limits (**irrelevant at 10–30 rows/day**)."* 10–30 rows/day is the **ingest rate**. The read is **cumulative**. The ADR sized a *stock* by its *flow*, and that single substitution is the entire outage. The limit became relevant on the day the accumulated stock crossed 1 MB — which for a monotonically growing table was never a question of *if*.
3. **How?** Latent since v0.1 and invisible until the table grew. The crash date (2026-07-25) is four days after the last commit (2026-07-21) — the outage began just as active development stopped, so no one was running the pipeline by hand any more. **Detection worked perfectly and changed nothing:** INV-002's `PipelineReturned500` alarm — built for precisely this class of failure — fired on all 38 days and SNS delivered **two emails per day** (ALARM + OK) to the operator. Confirmed in the operator's own inbox. The alarm had become so reliably daily that it was indistinguishable from the product it was reporting the absence of.
4. **How fixed?** Three parts, on branch `feat/gold-rejection-lineage` ([ADR-0036](../adr/0036-gold-filter-rejection-lineage.md)):
   - **Column projection.** `_SILVER_COLUMNS` / `_GOLD_COLUMNS` declared beside `_dissected_from_row` in `adapters/repository_postgres.py` so a projection and its mapper cannot drift; applied to `get_silver_postings` and `get_gold_candidates`. Single-row reads keep `select(tables.posting)`. **3,110 kB → 109 kB.**
   - **Rejection lineage** (migration `0007_gold_filter_hash`). A non-fit becomes `status='rejected'` stamped with `gold_filter_hash` — sha256 over the profile + spec + strategy name. `get_silver_postings(filter_hash=…)` returns unjudged rows plus rejections whose stamp `IS DISTINCT FROM` the current one. The read stops being O(all history) *without* freezing gold decisions: change `targeting.job_titles` and the whole rejected backlog re-opens, which the old "non-fits stay silver" behaviour provided by accident and which `reassess` cannot substitute for (it replays `status='scored'` rows only).
   - **A legible billing failure.** `LlmBillingError` (HTTP 402) is now its own type, never retried, counted as `billing_blocked` in the ingest summary and logged **once** with the operator action — instead of 137 identical per-item warnings.
5. **Prevention + Detection:** `tests/test_integration_gold_read_size.py` seeds rows with 1 MB of `description` and asserts the read payload does not grow with it, with a negative twin proving the projection still returns every mapped field. `tests/test_handler_helpers.py` asserts `compute_filter_hash` moves on a `targeting.job_titles` change **while `compute_profile_hash` provably does not** — the trap that would have made this fix silently lose jobs. `tests/test_gold_filter.py` pins the re-open, the no-re-read negative, and that a fail-open posting is never stamped rejected.
   **Detection — the honest answer: detection was never the gap.** The alarm existed, was correct, fired 38 times, and reached a human. No additional alarm would have helped; adding one would be treating the wrong failure. The two changes that address the actual gap are (a) the run summary is now self-describing — `billing_blocked` names its own cause where `{silvered: 0, skipped: 137}` looked like ordinary attrition; and (b) the **residual gap is recorded rather than papered over**: an alarm that fires every day is noise, and this project has no mechanism that escalates a *persistent* alarm differently from a one-off. That is a real open weakness, logged in the [backlog](backlog.md), not closed by this fix.
   **Second lesson, for capacity assumptions generally:** an ADR that dismisses a platform limit must state the quantity it measured. "Irrelevant at 10–30 rows/day" would have been visibly wrong the moment it was written next to "the read returns every row ever stored."
- **Blast radius:** 38 daily runs dead, **38 digests never sent** (2026-07-25 → 2026-09-01), zero data corruption — every run died on a *read*, before any write. Four more unbounded `.all()` reads share the same ceiling and are recorded in the [backlog](backlog.md): `get_gold_candidates` (fixed here by projection), `get_scored_for_reassess`, `get_scored_shortlist`, and `get_all_scored` (401 rows / 274 kB of LLM prose today — the next one to reach the wall).
- **Prevention implemented?** Yes — projection + migration 0007 + 13 unit tests + 6 integration tests (branch `feat/gold-rejection-lineage`). The LLM account top-up is an operator action, not a code fix.

### ERR-011 — Reasoning tokens ate the whole budget; the API returned HTTP 200 with an EMPTY completion   [Resolved]
- Stage: dissect + score (every LLM call) · Layer: LLM transport · Type: dependency (provider model behaviour changed under a fixed config) + a swallowed signal
- Discovered: 2026-09-01, while verifying the ERR-010 fix against the live API — **not** by the pipeline, which had been reporting it as malformed JSON for weeks · Resolved: 2026-09-01 (branch `feat/gold-rejection-lineage`) · Source: live probe

1. **What happened?** Live dissect and score calls returned **HTTP 200** with `finish_reason: "length"` and an **empty** `content`. Two layers up that surfaced as, verbatim:
   > `no valid extraction after one retry: no JSON object in model output: ''`

   Which is exactly what the 2026-08-22 production log shows, for every posting in that run. The message blames the model's formatting; the cause is nothing of the kind.
2. **Why?** DeepSeek's v4 models are **reasoners**: `max_tokens` budgets reasoning **and** content together, and reasoning runs **first**. Exhaust it and you get a well-formed 200 whose `content` is empty. Measured live with the real scorer prompt at the production `max_tokens=4096`: `completion_tokens=4096, reasoning_tokens=4096, content_chars=0` — **the model spent the entire budget thinking and emitted nothing.** `adapters/llm_openai.py` then did `data["choices"][0]["message"]["content"] or ""`, converting a truncation signal into an empty string and discarding `finish_reason` entirely. The scorer's one bad-JSON retry then re-prompted at the *same* budget, which cannot help, and the posting was counted as an isolated dissection failure.
3. **How?** A config that was correct when written stopped being correct when the provider's models became reasoners; nothing in the code could notice, because the one field that says "your answer was cut off" was never read. This is why the 2026-08-22 run looked like a model-quality problem and the 2026-08-31 run (by then also out of credit) looked like a billing problem — three distinct faults wearing the same symptom, `silvered: 0`.
4. **How fixed?** Two changes.
   - **Read the signal.** `complete()` now raises on `finish_reason == "length"` with a message naming `max_tokens`, the reasoning share, and the fix — instead of returning `""`. Per-item isolation is unchanged (it is an `LlmError`, already caught per posting), so one truncated posting still never kills a run.
   - **Budget per task, from measurement.** New `LlmConfig.reasoning` / `reasoning_effort`; `handlers/pipeline.py` gains `_dissect_llm_config()` and `_score_llm_config()`. **Extraction runs with reasoning OFF** (`thinking: {"type": "disabled"}`) — it fills a fixed JSON schema from text that already contains every answer, so reasoning buys nothing: measured **425 tokens** vs ~2,950 with it on, a ~7x saving. **Scoring keeps reasoning ON at `effort: "high"`** — postings word the same role very differently, so reconciling a JD against the profile is real work; keeping reasoning on is also what keeps v0.11.0's boundary calibration (avg spread 15.95 => resample margin 16) describing the model actually in use. **The fix was naming the effort, not lowering it:** omitting `reasoning_effort` leaves reasoning *uncapped*, which is what burned 4,096 tokens; explicit `high` measures **1,334-2,348 tokens** inside a 6,144 budget.
5. **Prevention + Detection:** four unit tests pin the truncation raise (including that `finish_reason` *absent* is NOT treated as truncation — a non-reasoning provider must still work), four pin the request body (the two reasoning keys are mutually exclusive; a default config sends neither, so ADR-0012 portability holds), three pin the per-task budgets. **Detection — the deeper fix:** the live tests built their **own** `LlmConfig`, so they proved that *some* configuration worked while production's was broken. They now call `_score_llm_config()` / `_dissect_llm_config()` directly, so a live run exercises the real budget. **Lesson: a test that constructs its own copy of production config tests the copy.** The same shape as the `ALEMBIC_HEAD` gap (backlog B-7).
   **Second lesson:** reasoning **expands to fill the budget offered** (886 tokens at `max_tokens=4096`, 1,412 at 6,144), so raising `max_tokens` is not a free safety margin — it buys more thinking and more cost, not more headroom. Budgets here have to be measured, not guessed generously.
- **Blast radius:** every LLM call on a real-sized posting. Compounded ERR-010: even with the 1 MB read fixed, the pipeline would have run cleanly and still produced **zero** silvered postings and **no digest**. `scripts/deepseek_smoke.py` reported **PASS** throughout — it asserts HTTP 200 and never checks that the reply is non-empty, which is precisely the presence-not-behaviour gate `CLAUDE.md` forbids.
- **Prevention implemented?** Yes — the raise, the measured per-task budgets, and 11 tests (branch `feat/gold-rejection-lineage`). Live-verified: the previously-failing `test_live_scorer` / `test_integration_deepseek` now pass against the real API.

### ERR-012 - A hard minor-version pin + AWS auto-minor-upgrade = Terraform tries to downgrade the live database on every apply   [Resolved]
- Stage: deploy (the ERR-010/011 release) - Layer: IaC / Aurora - Type: config (two settings that contradict each other)
- Discovered: 2026-09-01, when `terraform apply` for the ERR-010 fix failed - Resolved: 2026-09-01 (branch `fix/aurora-engine-version-drift`) - Source: implementation (deploy-time)

1. **What happened?** The deploy meant to end the 38-day outage errored out, verbatim:
   > `Error: updating RDS Cluster (jobfetcher-dev): api error InvalidParameterCombination: Cannot find upgrade target from 16.11 with requested version 16.6.`

   The plan had shown it clearly - `~ engine_version = "16.11" -> "16.6"` on **both** `aws_rds_cluster.main` and `aws_rds_cluster_instance.main`, alongside the intended Lambda update. A `-target`ed apply of only the Lambda did **not** avoid it: the Lambda depends on the cluster (its env vars carry the cluster ARN), so Terraform pulled the cluster in as a dependency, attempted it first, and failed before the Lambda was ever touched.
2. **Why?** `terraform/aurora.tf` hard-pinned `engine_version = "16.6"` while the cluster runs with `auto_minor_version_upgrade = true` (the AWS default, never overridden). Those two statements contradict each other: AWS owns the minor version and had patched the cluster to **16.11**, Terraform read that as drift and tried to push it back, and RDS does not support minor **downgrades**. The pin was correct the day it was written and became a landmine the moment AWS patched the cluster - which is the entire point of leaving auto-upgrade on.
3. **How?** Latent since v0.1 and invisible because nothing applied Terraform between the AWS bump and this deploy. The repo's own teardown cadence normally masks it too: a `destroy` + `apply` builds a fresh cluster at the pinned version, so the drift can only appear on a stack left **up** long enough for AWS to patch it. The 38-day outage is what left it up.
4. **How fixed?** `engine_version = "16"` - assert the **major** only and let `auto_minor_version_upgrade` own the minor, which is what was already true in fact. Zero effect on the running cluster (it stays 16.11); Terraform simply stops asserting a minor it does not control, while a **major** upgrade remains deliberate and explicit. Rejected: re-pinning to `16.11` (correct for a day, then AWS bumps again and the next deploy breaks identically) and `lifecycle { ignore_changes = [engine_version] }` (ends the diff but leaves the file stating a version that is not true, and would also silence a real major-version change).
5. **Prevention + Detection:** the contradiction can no longer be reintroduced silently - a minor pin under auto-upgrade would have to be written deliberately over the comment explaining why it must not be. **Detection - the honest gap:** CI runs `terraform validate` (syntax only) and **no `terraform plan`**, so configuration that validates but cannot apply is caught only by a human running the deploy. That is the same class of gap ERR-004/005 named (some failures exist only live), and it is why the [runbook](../runbooks/deploy.md) makes plan-then-read a step rather than an `-auto-approve`. A plan-on-PR job would have surfaced the downgrade before merge; recorded in the [backlog](backlog.md) alongside the IaC-scanning gap, not built here.
   **Lesson:** any attribute a cloud provider may change on its own - engine minor versions, certificate rotations, managed-key versions - must either be left un-asserted or explicitly ignored. Asserting it *and* delegating it is a contradiction that stays quiet until the provider acts.
- **Blast radius:** the deploy, not the data. The cluster was untouched and stayed `available` at 16.11 throughout - AWS rejected the `ModifyDBCluster` before any change. The Lambda simply did not update, leaving the schema at 0007 with the code still at 0006: harmless, because 0007 is additive, but it meant the outage fix was not live until this was resolved.
- **Prevention implemented?** Yes - `engine_version = "16"` + the in-file rationale (branch `fix/aurora-engine-version-drift`).

### ERR-013 - The ERR-010 fix was sized in the wrong units and did not work   [Resolved]
- Stage: deploy + first live run of the ERR-010 fix - Layer: persistence / RDS Data API - Type: logic (a correct fix, sized against the wrong measurement)
- Discovered: 2026-09-01, by the post-deploy live run - Resolved: 2026-09-01 (branch `fix/paginate-silver-read`) - Source: live validation

1. **What happened?** The ERR-010 fix deployed cleanly, the smoke gate returned `200 @ 0007_gold_filter_hash`, ingest worked for the first time in 38 days — `{'fetched': 20, 'silvered': 19, 'billing_blocked': 0}` — and then the run died at the **same** place with the **same** error:
   > `UnsupportedResultException: The result exceeds the size limit 1 MB.`
2. **Why?** The column projection was real and helped (3,110 kB -> ~1.4 MB), but it was **sized against the wrong number.** ERR-010 measured the needed columns with `pg_column_size()` and reported **109 kB**. That function returns the **COMPRESSED, TOASTed on-disk** size. The Data API serializes results as **uncompressed JSON text**. Measured live on the same rows: the `skills` JSONB is **537 kB on disk but 1,291 kB as text** — over the cap by itself, before any other column or JSON envelope. The projected read was never anywhere near 109 kB on the wire, so "28x headroom" was fiction and the follow-on reasoning built on it ("pagination is subsumed at this row count") was wrong.
3. **How?** A units error that survived because every check agreed with it. The regression test asserts on the **emitted SQL** (correctly — it proves `description` is not selected) and on **row payloads measured through psycopg2**, which is a different transport with no such cap and no JSON envelope. Nothing in the suite could observe a Data API response size, because there is no local Data API — the identical detection gap ERR-004 named and ERR-010 restated. The measurement that mattered was only ever available in production.
4. **How fixed?** **Keyset pagination** in `get_silver_postings` — walk `posting_id` in pages of `_SILVER_PAGE_SIZE = 200`, accumulate, return the whole set. Each round-trip is then bounded by page size instead of by table size, which is the property that was actually needed: projection reduces the constant, pagination removes the dependence on row count. Verified live: 1,000 rows passed and 1,041 failed, so 200 sits ~5x under the observed wall. `OFFSET` was rejected (it re-scans, and it skips rows if the set shifts mid-walk). Also raised the extraction budget 2048 -> 8192: the same run truncated one long posting at `content_chars=8273` with reasoning already off, so extraction output has a long tail that the measured 425-token typical hid.
5. **Prevention + Detection:** `tests/test_integration_gold_read_size.py` seeds `_SILVER_PAGE_SIZE + 37` rows (deliberately not a page multiple) and asserts every one returns exactly once in sorted order — a loop that stops after page one, serves a row twice, or never terminates all fail. A second test pins that `limit` caps the total rather than the page.
   **Detection - the gap that remains, stated plainly:** none of this could have been caught before production, and it still cannot. There is no local RDS Data API, so no test can measure the thing that failed. The honest mitigation is not a test, it is a **design rule**: behind a request/response API with a response cap, a read must be bounded by construction (paginated), never by an estimate of how big the data is. An estimate can be wrong about units; pagination cannot be wrong about row count.
   **Lesson:** `pg_column_size()` answers "how much disk does this occupy", not "how much will this weigh on the wire". For a JSONB column the gap is ~2.4x here, and compression means the gap grows with how repetitive the data is. When a limit applies to a serialized payload, measure the serialized payload.
- **Blast radius:** one failed post-deploy run. No data harm - it died on a read, as ERR-010 did. The outage continued ~1 hour longer than the deploy suggested.
- **Prevention implemented?** Yes - keyset pagination + 2 integration tests + the larger extraction budget (branch `fix/paginate-silver-read`).

### ERR-014 - The documented 500-concurrency limit is a ceiling, not an entitlement: the real cap is scaled to account balance (39)   [Resolved]
- Stage: backlog drain (raising `PIPELINE_MAX_WORKERS`) - Layer: LLM transport / provider quota - Type: dependency (a published limit that does not describe the account)
- Discovered: 2026-09-02, by running at 80 workers - Resolved: 2026-09-02 (branch `fix/concurrency-to-real-limit`) - Source: live run

1. **What happened?** `PIPELINE_MAX_WORKERS` was raised 8 -> 80 to drain the 698-posting backlog in one run. The run scored **exactly 80** postings - one full round of workers - and then stalled. Verbatim, from DeepSeek:
   > `HTTP 429: {"error":{"message":"Too many requests. Your current concurrency is 40, which exceeds your concurrency limit of 39 based on your remaining balance. Please top up your balance to restore your concurrency.","type":"rate_limit_error"}}`

   Final: `stage=score done {'gold': 698, 'scored': 80, 'failed': 618, 'deferred': 0}`.
2. **Why?** The published figure - `deepseek-v4-pro`: 500 concurrent - is a **ceiling, not an entitlement**. The effective limit is **scaled to the account's remaining balance**, and this account's real limit was **39**. 80 workers therefore exceeded it by 2x from the first moment; each worker's retries (3, with jitter) also failed, because the limit was structural rather than transient.
3. **How?** The number was researched properly - web sources agreed on 500, and the account was probed for `x-ratelimit-*` headers, which **do not exist**. There is no `/limits` endpoint either. **The only place DeepSeek states the real number is the body of a 429 you have already triggered.** So the true limit is unknowable before you exceed it: the sizing had to be wrong once to be right afterwards. The published number was accurate *and* inapplicable, which is the worst combination - it invites confident over-provisioning.
4. **How fixed?** `PIPELINE_MAX_WORKERS = 30` - ~23% under the observed 39. The headroom is not caution for its own sake: the limit **moves with balance**, so a value near the cap is safe at the start of a run and unsafe by the end of it. Topping up the balance raises the ceiling and would allow more.
5. **Prevention + Detection:** the reasoning, the measured 39, and *why the margin exists* are recorded inline in `terraform/lambda.tf` beside the value, since the next person to raise it will otherwise re-derive 500 from the same public docs and repeat this exactly. **Detection:** the failure is already loud and precise - `failed: 618` in the run summary plus the verbatim 429 naming the real number. Nothing needs adding; the run summary said exactly what was wrong.
   **Lesson:** a published rate limit describes the *product*, not *your account*. Where a provider scales limits by spend, tier, or balance, the only authoritative source is the error it returns - so provision below the documented number and let the first 429 tell you the truth, rather than trusting a figure that was never about you.
- **Blast radius:** one wasted drain run (618 failed scorings, no tokens spent - 429s are rejected before inference). **The run still sent a digest** (`notify.sent: 1`) off the 564 already-scored postings: the first since 2026-07-24. The backlog stands at 618.
- **Prevention implemented?** Yes - the corrected value plus the inline rationale (branch `fix/concurrency-to-real-limit`).

1. **What happened?** The project's first pillar — *"the repo is the memory: any session resumes from these files alone"* — was **measurably false**, in ways a command could prove:
   - **A public write endpoint was invisible.** `handlers/capture.py` is a Lambda Function URL with `authorization_type = "NONE"` — the project's only internet-facing write surface. It shipped 2026-07-20 and was live-validated. Three units later it appeared in **none** of `README.md`, `CLAUDE.md`, `02-architecture.md`, `diagrams.md`. A reader could finish the README and not know the deployed stack accepts writes from the internet.
   - **26 broken internal links**, 21 of them one systematic error in `session-log/working-document.md`.
   - **28 citations of `plan §NN`** across 9 files — including 6 ADRs and `decisions-locked.md` — pointing at a document readers could not reach. (§12–§29 *were* in the repo, unlinked; §30+ were never committed at all.)
   - **Two release-discipline promises unkept across 15 tags:** a before/after diagram per release (zero produced, promised in three places incl. ADR-0001), and an `UPGRADING` note (no such file, ever).
   - **A documented gate that would fail if run:** `/review-step` Check 1 claimed to enforce `ruff format --check`; the tree is 84 files from clean and CI never ran it ([B-11](backlog.md)).
2. **Why?** Two mechanical causes, and the second is the one that matters.
   - **No fact has an owning file.** Content was copy-pasted rather than linked, so every release required hand-syncing **~27,700 words** across `CHANGELOG.md`, `phase-index.md`, `interface-contracts.md`, `README.md`, `CLAUDE.md` and `03-roadmap.md`. The worst case: `CLAUDE.md` had become a second CHANGELOG — eleven per-release paragraphs carrying ~15 numbers owned elsewhere. *(Counting files that mention a given measurement — `"286 rows"` in 12, `"15.95"` in 10 — overstates this and is the wrong metric: those are **historical** figures, frozen when taken and incapable of drifting, each sitting in the ledger row it is evidence for. See [05-methodology](../05-methodology.md#one-canonical-home-per-fact-err-016).)*
   - **Derived counts were typed as prose literals** — test totals, resource counts, release counts. A literal is correct only at the instant it is written. **And nothing failed when one went stale.** Lint passed, tests passed, CI was green, the release shipped. Doc drift was the one defect class in this repo with *no* detector.
3. **How?** The 2026-08-31 audit found a clean split: **everything the close-out checklist named was current; everything it did not name had drifted.** The checklist was then amended (`.agents/agentic-workflow.md` step 6) to name the five omitted docs — `errors.md`, `README.md`, `CLAUDE.md`, `02-architecture.md`, `diagrams.md` — closing with *"This is a checklist, not a suggestion."* **Two days later the capture endpoint was still missing from four of those five.** The checklist was written and immediately not followed. Meanwhile the ERR-010 close-out corrected "21 resources"→32, "2 alarms"→3, "466 tests"→512 — and **the test figure was stale again within two days** (531→549), because the same session that fixed it added tests. The debt was cleared twice and regenerated twice.
4. **How fixed?** Six PRs, deliberately split by theme (#50–#55). #50 the wrong facts + 24 of the 26 links; #51 the capture endpoint into all four entry-point docs (+ INV-002, the other unit missing from the as-built ladder); #52 the two promises **retracted in the text, never silently deleted** — ADR-0001 gets a dated retrospective *appended*, because what it believed in 2026-06 is the useful record; #53 the `plan §NN` citations (§12–§29 linked to `working-document.md`, §30+ re-pointed to in-repo successors and labelled as never-committed); #54 **`scripts/check_docs.py` wired into CI**; #55 fact ownership, the honest `/review-step`, and this entry.
5. **Prevention + Detection:** **`scripts/check_docs.py`, in the `lint-and-test` job.** It fails the build on a broken internal link, a `plan §NN` citation, a **guarded prose count that disagrees with the command that produces it**, or a stale deployment claim. Counts are marked in prose with a non-rendering HTML comment naming their fact (`<!--fact:tests-->…<!--/fact-->`); the script runs `pytest --collect-only`, counts `^resource ` in `terraform/*.tf`, counts CHANGELOG release headings, and diffs. That is the half that converts a recurring manual chore into a build failure. **Detection:** the same script, on every PR — the class previously had none.
   **Explicitly NOT "be more careful."** The two prior clearings of this debt were both careful, and both regenerated within a day. Care is not a control.
   **Judged against ERR-015's test — what happens when someone ignores it?** `lint-and-test` is a required status check on `main`, and protection has `enforce_admins: true`, so a stale guarded count blocks the merge for everyone including the repo owner. **And the gate was proven by watching it fail, not by assertion:** a deliberate regression (a guarded count bumped 549→550 with no test added) was pushed, CI went red in the `Doc audit` step naming the exact number, and the revert went green — [run 33807955964](https://github.com/tarigelamin1997/jobfetcher/actions/runs/33807955964) red, [run 33808062603](https://github.com/tarigelamin1997/jobfetcher/actions/runs/33808062603) green. Same standard ERR-015 was closed to.
   **The residual, stated rather than papered over:** the script cannot tell whether a *new* surface belongs in `02-architecture.md`. That judgement stays human and stays in the close-out checklist. What is mechanical is now mechanical; what is not is labelled as not.
- **Blast radius:** no production impact — the tool ran (and failed) on its own schedule regardless. The cost is to the property the project is explicitly built on: a fresh session (human or agent) resuming from the repo alone would have been misled about the deployed attack surface, followed dead citations into a document that isn't there, and trusted counts that were wrong.
- **Prevention implemented?** Yes — `scripts/check_docs.py` in CI, verified by a watched failure; the debt itself cleared in PRs #50–#55; the honesty gap in `/review-step` closed and its remainder logged as [B-11](backlog.md).
